# Communications module

Owns two separate event-scoped communication paths:

- Staff announcements with draft and published event-feed states.
- Versioned registration message templates, event sender/reply-to settings, transactional outbox rows, immutable rendered snapshots, reviewed balance-reminder batches, corrected-address confirmation copies, local or external delivery attempts, provider-event history, and audited staff retries.

## Registration message behavior

Public registration queues its registrant confirmation and one internal notice per configured internal recipient inside the same serializable transaction as the registration. The outbox uses a deterministic idempotency key, so an identical registration replay cannot create duplicate messages. Rendering uses an allow-listed plaintext token set; unknown tokens and multiline subjects are rejected when staff publish a new template version.

After the transaction commits, `LOCAL_CAPTURE` records a `CAPTURED` attempt without calling a provider. `EXTERNAL_EMAIL` claims rows for Resend with stable idempotency, stale-lock recovery, exponential backoff, and delivery-event reconciliation. `DISABLED` preserves a suppressed outbox row for auditing. Delivery failure never rolls a successful registration, lifecycle change, contact edit, or payment back.

The initial template set contains:

1. Paid/no-balance registration confirmation.
2. Unpaid/balance-due registration confirmation.
3. Worker confirmation.
4. Internal new-registration notice.
5. Waitlist entry.
6. Waitlist promotion.
7. Registration cancellation.
8. Contact-details update.
9. Square payment receipt.
10. Balance reminder.
11. Whole-registration transfer notice for the new contact.
12. Whole-registration transfer notice for the prior contact.
13. Attendee-substitution notice.

Staff can publish new immutable versions, inspect exact snapshots and delivery attempts, create a fictitious local test, process pending rows, and create an audited retry. Every generic retry requires a client UUID plus the server-issued SHA-256 fingerprint of the selected immutable source and current delivery mode. A lost-response replay with the exact pair returns the same child row; reusing the UUID for another source or fingerprint returns `IDEMPOTENCY_KEY_REUSED`. The retry transaction only snapshots and audits the child. Local capture or provider processing starts after commit.

Private management URLs are inserted in memory at delivery time from deterministic HMAC tokens; the raw bearer URL is never stored in the outbox, operation snapshots, audit metadata, API response, or logs. Transfer and substitution operations initialize their event's published template versions before mutation, queue the immutable rendered notices inside the business transaction, and process local or external delivery only after that transaction commits. The new transfer contact's replacement access row is also issued only after commit.

## Message bodies, HTML, and generated blocks

A template body is authored, validated, and stored as one plain-text Markdown source. Both parts of the message are rendered from that source and the same token context in one `renderMessageTemplate` call and snapshotted together on the outbox row (`bodyTextSnapshot`, `bodyHtmlSnapshot`), so the two parts cannot drift and a captured row keeps meaning exactly what it said when it was captured. Delivery wraps the stored fragment in the email layout; it does not re-render it. Rows queued before HTML bodies existed have no fragment and go out as text only.

Two separate protections apply, because they answer different attacks. First, the renderer escapes the whole source before it looks for any markup, then recognises a small subset — headings, bold, italic, code, ordered and unordered lists, rules, images, and links restricted to `http`, `https`, `mailto`, and `tel` — so nothing in a body can introduce a tag, an attribute, or a script.

Second, HTML escaping alone does not stop *Markdown* injection: a registrant named `[Review your registration](https://malicious.example)` would otherwise get a trusted-looking link, and `![](…)` a tracking pixel, into mail sent from the IMSDA address. So untrusted token values are Markdown-escaped before substitution, and only `MARKDOWN_MESSAGE_TEMPLATE_TOKENS` — the generated blocks, the URL tokens that sit inside `[text](…)`, and the staff-authored `announcement_body` — carry live Markdown. `attendee_summary` is deliberately not in that set: it is built from registrant names and submitted answers, so it renders as plain lines rather than a list. The escapes are dropped again while rendering, and the plain-text part substitutes the raw value, so no reader ever sees a backslash.

This is also why the HTML is rendered at enqueue rather than at delivery. Only there are the trusted and untrusted spans of a body still distinguishable; the finished text cannot tell a template's Markdown from a registrant's.

Rendering at enqueue has one consequence worth knowing before touching `email-html.ts`: a body is rendered *before* any private token exists, so its portal link and pass image carry the delivery sentinels rather than URLs. The renderer accepts those as a third, internal URL class, matched by exact shape rather than by prefix. If it did not, scheme validation would reject them, and a rejected link is rendered as inert text — which strips the `href` and `src` and leaves delivery nothing to substitute, so every HTML email loses its buttons and its QR while the plain-text part still looks correct. `tests/delivery-sentinel-round-trip.test.ts` pins that whole path, because preview tests use ordinary HTTPS sample URLs and never exercise it.

Some sections depend on the event or on the registration's state rather than on the template. Those are server-generated blocks (`message-blocks.ts`), placed by a single token and emitted as Markdown like everything else:

- `{{hotel_information}}` — the event's configured lodging. Omitted entirely when the event has no hotel name, which is why lodging is per-event columns rather than text embedded in a shared template.
- `{{payment_status_block}}` — the paid, balance-due, complimentary, waitlisted, promoted, or cancelled section for this registration's actual state. The trigger decides the state, not the arithmetic: a waitlist confirmation with a nonzero total still says no payment is due.
- `{{checkin_block}}`, `{{checkin_qr_url}}` ("Check-in page link"), `{{checkin_qr_image}}` ("Check-in QR code (image)"), `{{checkin_qr_images}}` — check-in instructions and the attendee pass QR, written against the delivery sentinels. A pass resolves one attendee, so outside event announcements a QR is inlined only for a single-attendee registration; a party is sent to the portal, where each attendee has their own labelled pass. Inlining the first attendee's code for a family would check that person in and leave the rest holding a code that is not theirs. **Event announcements** to a party instead show every attendee's own QR, each labelled with the attendee's name, so each code sits next to the person it checks in: the body's `![…]({{checkin_qr_image}})` becomes `{{checkin_qr_images}}` and `{{checkin_block}}` lists them. Each image is a per-pass sentinel URL that delivery resolves with the same registration token (the pass route authorizes only that registration's attendees). `{{checkin_qr_url}}` is a page link and prints a web address when left bare; the editor warns about that.
- `{{seminar_preferences}}` — each attendee's name, their assigned seminar where the seminar assignments module has a current assignment, and their ranked choices from the form's seminar field(s), built server-side from each registration's own answers (Markdown-escaped). A real test send that names a registration never uses sample values for any token: a missing value renders empty, or `(none)` for a required token.

These tokens are optional: an empty value renders as nothing rather than leaving `{{token}}` in the body and stopping the send, and the surrounding blank lines close back up.

`{{contact_email}}` is the event organiser's published contact address — the one a "questions? contact …" line means. The registration's own destination is `{{registration_contact_email}}`, and `{{reply_to_email}}` remains the delivery header configured in message settings. The migration that introduced the split rewrote every stored template version from the old `{{contact_email}}` to `{{registration_contact_email}}`, so an already-published template kept rendering exactly the value it rendered before. Because the parser trims arbitrary whitespace inside the braces, that rewrite is a regular expression rather than a literal replacement: `{{ contact_email}}` and `{{contact_email  }}` are equally valid spellings staff may have saved, and a missed one would have silently changed meaning at deploy.

Preview in the workspace renders the same HTML delivery sends, inside a fully sandboxed iframe, with the delivery sentinels replaced by valid but obviously non-live URLs. It uses the one sample context the server also uses, rather than a second copy: the copies had drifted, and the preview was pairing one event's dates and venue with another event's lodging.

## Attachments, embedded pictures, and buttons (#824)

Staff can attach files to a template version or a draft announcement, put an uploaded picture in a body, and add a button. All three ride on the same rules as the rest of the body: nothing a registrant supplies can become one of them.

- **Files** (`message-files.ts`, `message-file-rules.ts`). A file is PDF, PNG, JPEG, WebP, DOCX, XLSX or PPTX, decided by its **bytes** in `message-file-sniff.ts` (the type a browser sends is ignored). An Office file is a ZIP package, so its central directory is parsed and entry names are matched exactly (a stored text file that merely mentions `word/document.xml` is not a document); `[Content_Types].xml` is inflated under a 256 KB bound, and a package that declares a macro-enabled content type or carries a `vbaProject.bin` is refused. Each attachment is at most 10 MB (the upload route also refuses a declared `content-length` over 10.5 MB before reading the body), a message's attachments together at most 20 MB and 10 files, a picture for a body at most 2 MB, an event at most 200 files, and a message at most 30 embedded pictures and 6 MB of them. Those message limits are checked when a template version is published and when an announcement is saved, and again when a message is queued, so delivery never has to drop anything. A file is stored privately through the event asset storage helpers under a generated name (`message-files/<event>/<uuid>.<ext>`); the uploaded name is kept only as a cleaned display label. Staff download one through `/api/events/:eventId/message-files/:fileId`, which needs `MANAGE_COMMUNICATIONS` for that event and serves it under its verified type with `nosniff` and a sandboxed CSP. The audit trail records file names and sizes only. The foreign keys from the link tables to `MessageFile` are RESTRICT: a file anything refers to cannot be deleted, and event deletion removes the outbox rows, announcements and template versions first and then the files (and their bytes on disk).
- **Where they come from.** Publishing a template version takes `attachmentFileIds`; leaving it out carries the previous version's files forward, and sending the list without a file removes it. An announcement's files are set while it is a draft. When a message is queued, `linkQueuedMessageFiles` writes `MessageOutboxFile` rows (the template version's files, the announcement's, and every uploaded picture the rendered HTML embeds). Those rows are the durable reference: delivery reads only them, so every attempt, the retry after a transient failure, and a staff retry or resend copy send the same files. A staff retry copy also keeps the formatted part of the message.
- **Delivery** (`email-attachments.ts`). Each file is sent as a real attachment. Each picture the HTML shows becomes an inline part with a `content_id` and its `<img src>` becomes `cid:<id>`, so Outlook shows it without "download pictures". Uploaded pictures (`![alt](msgfile:<id>)`) are read from storage and checked against their hash; the check-in QR is rendered **in-process** from the pass (the same `createAuthorizedAttendeePass` check the pass route makes, and only for a URL on this app's own origin), not fetched over HTTP. Only a QR falls back: if it cannot be embedded its remote URL stays as before (the count is logged). An uploaded picture or an attachment that is missing, unreadable or no longer matches its recorded hash **fails the message**, never a send without it; the error is typed (`MessageFileDeliveryError`), has a generic message with no path, and is retryable only for transient I/O (`EIO`, `EMFILE`, ...). A file is read and hash-checked once per delivery run however many messages carry it. An announcement broadcast whose messages carry files is not delivered inside the staff request: the outbox worker (`outbox-sweep.ts` runs `processPendingMessages` for every event holding due messages) sends them.
- **Buttons.** `[Text](url){.button}` alone on a line is rendered as a table-based button (cell colour and `mso-padding-alt` for Outlook). Inside a sentence the same syntax is an ordinary link and the marker is dropped. The destination goes through the same scheme check as any link; an unsafe one renders as plain text. The plain-text part drops the marker, and an uploaded picture there is `[Image: description]`.
- **Previews.** The template preview and the delivery log list the files, and a test send carries the same ones a real message would. Pictures in a sandboxed preview load as data from the staff-only file route.
- **Not done here.** A file uploaded and never saved on a template or announcement stays in storage until the event is deleted; there is no scheduled sweep of such orphans and no storage quota beyond the per-event file count (follow-up issue #845).

## Send check and the inbox preview line (#836)

`send-check.ts` is one pure function, `runSendCheck`, that the template editor, template publish, the announcement composer and the announcement send review all call on the same text. It returns **errors**, **warnings** and **suggestions**, each with a `code`, a stable `id` (`CODE:n`), a `field` (`subject`, `body` or `preheader`) and an `anchor`, the id of the form field the screen jumps to (`TEMPLATE_CHECK_ANCHORS`, `ANNOUNCEMENT_CHECK_ANCHORS`).

- **Errors** (stop a publish or a send): an empty subject or body; a subject or preview line with a line break; a preview line holding a link, picture or generated-block token (`portal_url`, `checkin_qr_*`, `announcement_body`, `seminar_preferences` and the other blocks); a token off the allow-list; a link or button that is not `http`, `https`, `mailto`, `tel` or one of the two link tokens (it would render as plain text); a picture that is not a public `https://` address, an uploaded `msgfile:` picture or `{{checkin_qr_image}}`. Template publish (`publishMessageTemplateVersion`) refuses with `INVALID_TEMPLATE` and the findings, and the announcement send (`broadcastPublishedAnnouncement`) refuses with `SEND_CHECK_FAILED`. The browser only shows them early.
- **Warnings** (a send needs them acknowledged; a template publish is never held up by them): a subject over about 70 characters (measured with the token values the reader will see), a picture with no alt text, a bare `{{checkin_qr_url}}` (the rule is `checkin-qr-rule.ts`, shared with the body editor, not copied), and a link or button whose text is a web address. The review dialog's checkbox sends the ids it covers as `acknowledgedWarningIds`, and the server refuses with `WARNINGS_NOT_ACKNOWLEDGED` unless every warning it finds now is in the list.
- **Suggestions** (never block): no preview line; a very short body.

Which path runs which check:

| Path | Check |
| --- | --- |
| Template publish (`publishMessageTemplateVersion`) | errors block; warnings and suggestions shown only |
| Applying an event template (`templateMessageDefaultSchema`) | errors block |
| Announcement broadcast review and send | errors block; warnings need acknowledging |
| Scheduled announcement emails (`buildScheduledEmailReview`, used by create, edit and approve) | errors block |
| "Email selected" announcement (selected-audience send in `messaging-repository`) | errors block |

The last two use `assertAnnouncementTextSendable` (`announcement-send-check.ts`) and refuse with `INVALID_TEMPLATE` and the findings. Warnings are acknowledged only in the broadcast review. Event clones copy versions that already passed publish.

The announcement's title and text are token values at send time, so a `{{token}}` typed inside them is printed as written and never expanded. They are checked that way: no allow-list error for `{{favorite}}`, and a link whose target is a token is a link error because it would send as plain text.

An announcement is checked as the email it will become (`announcementSendCheckInput`): the event announcement template's subject and body, with the announcement's title and text where the tokens stand, and the announcement's own preview line, or the template's.

The **preview line** (preheader) is plain text of at most 150 characters on one line. It is stored on the immutable `MessageTemplateVersion.preheaderTemplate` and on `Announcement.preheader`, rendered at enqueue by `renderMessageTemplate` under the subject's rules (the same token allow-list, no Markdown, values not escaped), snapshotted as `MessageOutbox.preheaderSnapshot`, and written by `renderEmailHtmlDocument` as a hidden block right after `<body>` (HTML-escaped there, followed by filler so the body's first words do not fill the preview). It appears in the template preview, the delivery log, the review dialog and test sends. A message with no line has a null snapshot, writes no column, and its document is byte for byte what it was before; `tests/email-preview-line-836.test.ts` pins that against the output of the earlier renderer. Event clones and event templates do not copy the line yet.

## Balance-reminder workflow

The Reminders tab is a two-step staff workflow. Its read-only preview considers every event registration, but includes a recipient only when all three rules are true:

1. The registration status is `SUBMITTED` or `CONFIRMED`.
2. Registration total minus successful payments plus successful refunds is greater than zero.
3. The registration contact snapshot (falling back to the account holder) contains a valid email.

The preview shows included and skipped counts, one mutually exclusive skip reason per omitted registration, the total outstanding balance, and every destination row. Its SHA-256 fingerprint covers the recipient rows, balances, skip counts, published template version, template enabled state, sender snapshots, delivery mode, and event text used for rendering.

Creating a batch requires that exact fingerprint plus a client-generated UUID. The server recomputes new batches in a serializable transaction and returns `409` if anything changed. Each outbox row is idempotent on event, batch UUID, and registration. A lost-response retry reads the audited batch before recalculation: the same UUID and fingerprint returns the original operation, while the same UUID with a different fingerprint is rejected. One audit row is protected by a partial unique index.

- `DISABLED` records suppressed rows and never sends.
- `LOCAL_CAPTURE` captures rendered local attempts and never contacts Resend.
- `EXTERNAL_EMAIL` creates pending rows only. Staff must separately use **Process email queue** before any provider call.

## Confirmation-copy workflow

An original terminal registrant confirmation can be copied from the Delivery log. Staff may enter a validated corrected email for that copy only. The source subject, body, sender, reply-to, registration link sentinel, and template-version reference are copied unchanged; neither `Person` nor the registration contact snapshot is updated.

The action requires a client UUID. Repeating that UUID returns the previously stored destination and row. Corrected confirmation copies and generic staff retries share one database-enforced active-child invariant: a second action is rejected while any child of the same source is `PENDING` or `PROCESSING`. A later intentional copy is allowed after the prior child reaches a terminal state. Local mode captures only, disabled mode suppresses, and external mode queues without automatically processing.

## Current boundary

Resend is the only external provider adapter and remains disabled until credentials and an event sender address are configured. SMS, push, and targeted/scheduled announcement delivery remain future work.

## Announcement unsubscribe and preferences (#838)

Only event announcements (`EVENT_ANNOUNCEMENT`) can be opted out of. Confirmations, receipts, waitlist and transfer notices, balance reminders, and safety or schedule-change notices always go; nothing in the opt-out path looks at any other template.

- **Where the preference lives.** `EmailAnnouncementOptOut`, keyed on the normalised email address, so it follows the address across registrations and events. A row covers one event (`EVENT`) or every IMSDA Events announcement (`ALL`). Recording is idempotent and audited with the scope and source, never the address.
- **The link.** Each announcement carries an opaque token (`email-preferences.ts`): 43 URL-safe characters of HMAC output that hold no address, event or registration data, so nothing sensitive reaches a request log, path or header (`/unsubscribe/` and `/api/public/unsubscribe/` are also redacted in logged paths). Delivery records it in `EmailUnsubscribeToken` (only its SHA-256, with the address and event) and the link is looked up, so it keeps working after `MANAGE_LINK_DERIVATION_SECRET` is rotated. It is never stored in an outbox row. The public page `/unsubscribe/[token]` shows the address masked and offers "this event", "all announcements", and re-subscribe; each is a button that POSTs, because a GET (link scanners, previews) never changes anything.
- **One click.** `POST /api/public/unsubscribe/[token]` with `List-Unsubscribe=One-Click` (RFC 8058) needs no login and no CSRF token: the signed token is the authorisation, and it opts that address out of that event only. The body is read as a form, so urlencoded and multipart both work. An unknown or malformed token is a bare 404, for GET as well as POST.
- **Headers.** Both providers (`integrations/email`, Resend and SES over SMTP) send `List-Unsubscribe` and `List-Unsubscribe-Post` when the message input carries `listUnsubscribe`.
- **Applying it.** The broadcast review and the send read the same opt-outs, skip opted-out contacts and count them by kind, and the fingerprint covers them, so a review made before someone opted out is refused as stale. Delivery checks again immediately before the provider call, so an address that opted out while a message waited is skipped: the row ends `SUPPRESSED` with a reason and an audit row (ids and scope only). If the opt-out cannot be checked, the message is retried, never sent. A staff-chosen batch of the announcement template (Email selected, the People page's choice-answer email) honours opt-outs too, counting each skip with its reason; it has no announcement to mark essential.
- **Essential.** An event manager or above (`CONFIGURE_EVENT`) can mark an announcement essential so it reaches people who opted out; the review says how many opted-out contacts it will still reach. Marking and clearing are audited with the actor. Delivery reads the mark from the announcement (through the message's `announcementId`, which retry copies keep) when each message is sent, so clearing it applies to messages still queued. In production a non-https `APP_BASE_URL` omits the one-click headers and logs a warning.
- **Staff visibility.** The Emails page lists who opted out of the event, the People page marks the registration, and the review shows how many will be skipped and why.


## Reviewed event audience builder (#176, preview only)

`audience-query.ts`, `audience-resolve.ts` and `audience-repository.ts`, behind `GET`/`POST /api/events/:eventId/audience`, extend the WR26 selected-audience, balance-reminder and announcement review services: the same contact rule (contact snapshot, then account holder), the same net-paid balance and organization-billing rule, the same announcement opt-outs (#838), and the same review pattern as #316/#332 (a client UUID, the server's fingerprint, replay returns the original, a changed audience is `PREVIEW_CHANGED`). It does not replace them, and it does not send, queue or schedule anything. Sending and scheduling stay human-gated; scheduling is the "Scheduled email batches" section below (#177).

- **Query.** A strict, versioned (`audience-query/2`), normalized query: `messageKind`, recipient `roles` (registration contact, attendee, group billing contact, approved organization contact), `readinessStates` (one normalized status), and `search`. **`search` is the operations search (#180)**: the canonical URL-safe query string the staff lists use (`status=CONFIRMED&payment=UNPAID,PARTIAL&tag=<id>`), parsed, resolved against the event's catalog and run by `operations-search-domain.ts` and `operations-search-repository.ts`. The builder has no query engine of its own: lifecycle, attendee type, source, organization, location, waitlist, payment state, check-in, tags, form answers and text are exactly those filters, with their stable keys, their per-domain permissions and their never-searchable list (note bodies, consent evidence, health and sensitive answers, event membership). Normalization re-serializes the search canonically, drops sort and paging (presentation), refuses DRAFT, and defaults the lifecycle to submitted and confirmed, so the same audience written two ways has one hash. Unknown keys are validation errors. Phase 2 lodging, session and volunteer segments are not offered (they do not exist yet), and there are no saved views yet to select from; a saved view will be one `search` string.
- **Availability.** The caller's own event permissions go to the search unchanged (`searchViewerFor`), so a filter they may not use (payment needs `MANAGE_FINANCE`, tags `MANAGE_REGISTRATION` or `VIEW_SENSITIVE_DATA`, check-in `MANAGE_CHECK_IN` or `MANAGE_REGISTRATION`, text, organization and form answers `VIEW_SENSITIVE_DATA`) is refused before any read. The audience adds checks of its own: a role needs its domain (group billing contacts need a group registration on the event; organization contacts need a club or organization-billed registration) **and its permission on top of `MANAGE_COMMUNICATIONS`**: the attendee and group billing contact roles need `VIEW_SENSITIVE_DATA` (they reach people by name and address), the organization contact role needs `MANAGE_FINANCE` (it is billing data), and the registration contact needs nothing more. With the attendee role, free text, a check-in state and an attendee-scoped form answer are refused, because only the attendee-type and tag filters are decided per attendee. Readiness needs `MANAGE_REGISTRATION`. The `GROUP_LEADER` key is kept for stored queries; the person it names is the group registration's billing person (`groupRegistration.billingPerson`), and its label is "Group billing contact".
- **Minors.** Fail closed. An attendee is written to only when their attendee type is an adult type: `EventAttendeeType.minimumAge` of 18 or more, decided from the type and never from a birth date (ADR 0005 Addendum A). Every other attendee is excluded as `MINOR_ATTENDEE`, one address-free exclusion row per registration, role and reason: a maximum age under 18 is worded "under 18"; no age range, an open-ended range such as 10 and over, and no type definition at all are worded "age group is unknown". There is no event-level exception, so an event whose types have no ages set reaches no attendees until an administrator sets the adult type's minimum age to 18. This stays until the owner decides how minors may be messaged; the registration contact role is unaffected.
- **Loader consistency.** Tag assignments are read exactly as the search reads them (an inactive tag is still a tag). A registration is re-checked against the audience's statuses when each batch is loaded, so one cancelled after the ids were enumerated drops out. Provider suppression compares addresses lower-cased in one bounded query per chunk; a statement timeout or expired transaction there is `AUDIENCE_TOO_BROAD` (409), not a 500. A snapshot id is only ever read inside its own event.
Every refusal (not permitted, not on this event, another event's tag, a form question that is stale or sensitive, a malformed value) is one fixed 403 that names no filter, value or count, and the filter list is `availableOperationsFilters` (minus DRAFT), so it omits what the caller may not use.
- **Large audiences.** `enumerateOperationsRegistrationIds` (added to the search service for this) returns every matching registration id in one repeatable-read transaction, with the same `prepare` and `readWhere` as a paged search, under the same statement timeout. It is bounded by the paging limits (`MAX_PAGE` x `MAX_PAGE_SIZE`, 20,000): a larger match is refused (`AUDIENCE_TOO_BROAD`, 409) and never truncated into a set that looks complete. The builder loads the ids in batches (250 by default) and folds them into a compact per-address summary, so memory holds one batch plus that summary. Counts and the fingerprint always cover the whole audience, and `recipients` or `exclusions` come back as keyset pages (default 50, at most 200, opaque cursor).
- **Protected data.** The loader selects an explicit column list. It never reads profile snapshots, form answers (only whether any exists, decided in the database), health, screening or consent evidence, note rows or staff membership, so none of it can qualify or appear. A test fails if the loader names one.
- **Roles and de-duplication.** Candidates fold by normalized email, in any arrival order. A recipient lists all its roles and every rule that qualified it, and keeps one entry per registration with that registration's own balance, so two registrations sharing an address are two message targets, never one merged confirmation. Exclusions are listed with a reason: no or invalid address, an announcement opt-out (event or all), or a provider bounce or spam complaint as the address's latest delivery state. An operational audience ignores an announcement opt-out but not a bounce. Only a verified, current organization billing contact is an approved organization contact.
- **Fingerprint.** SHA-256 over the fingerprint version, query version, event, normalized query, each address with its roles and registrations (id, code, roles, balance) and every exclusion. It leaves out names and timestamps, and is identical across batch sizes and row order.
- **Snapshot.** `mode: "snapshot"` stores the normalized query (including its canonical `search`), its hash and version (`audience-query/2`), the fingerprint and counts in `EventAudienceSnapshot` (no recipient, address or name) and writes one audit row of ids and counts. It needs the fingerprint that was previewed.
- **Real-database check:** `npm run test:event-audience-builder`.

## Scheduled email batches (#177)

`scheduled-email-domain.ts` (pure), `scheduled-email-repository.ts` and `scheduled-email-options.ts` (client-safe labels), behind `GET`/`POST /api/events/:eventId/scheduled-emails` and `/api/events/:eventId/scheduled-emails/:scheduleId`, and the staff page `/communications/scheduled`. They extend the reviewed audience builder (#176: the query, the audience, the fingerprint) and the durable outbox (one `MessageOutbox` row per recipient, delivered by the existing worker). A schedule sends through `enqueueSelectedAudienceMessage`, so the template rendering, delivery-mode suppression, private links and unsubscribe handling are exactly those of every other message.

**Human gate.** Bulk email needs a person. A schedule is saved as `SCHEDULED`, which sends nothing. Only an authorized staff member's explicit approval (`activate`, with the review fingerprint they were shown) makes it `ACTIVE`, and the only automatic step is the outbox sweep sending a schedule that is already `ACTIVE` at its time. Every route needs `MANAGE_COMMUNICATIONS` for the event, and the audience is built with the caller's own permissions.

- **States.** `SCHEDULED` (written and reviewed, not approved), `ACTIVE` (approved; sending once it has been claimed), `PAUSED`, `CANCELLED`, `COMPLETED` (nothing waiting and nothing left to queue), `FAILED`. Editing an approved or paused schedule withdraws the approval (`SCHEDULED`, revision + 1); pause is possible only before a worker has claimed it; cancel works at any point before `COMPLETED`.
- **Event time.** A rule is `ONE_TIME` (a date and a wall-clock time), `BEFORE_REGISTRATION_CLOSE`, `BEFORE_EVENT_START` or `BEFORE_PAYMENT_DUE` (calendar days before the anchor day, at a wall-clock time), always in the event's own time zone. The registration close anchor is `Event.registrationClosesOn`, which is open through that whole day, so it closes at local midnight ending it. `BEFORE_PAYMENT_DUE` (#993) counts back from `Event.paymentDueOn`, due through that whole day like the close date. Owner decision (Oct 20, 2026): the due date is only a date to count back from. It adds no late fee, blocks nothing and changes no wording; a batch using it goes only to registrations that still owe a balance, decided again at send time from the same balance the balance reminder uses (otherwise `NO_BALANCE_DUE`). Changing or clearing the date after approval pauses the schedule for a new review, like a changed time zone or start. **DST is explicit:** a time that does not exist (spring forward) goes out at the first moment after the jump (`GAP_SHIFTED`, 02:30 becomes 03:30); a time that happens twice (fall back) goes out the first time (`AMBIGUOUS_FIRST`). "N days before" counts calendar days, so 09:00 stays 09:00 across a clock change. The review states the outcome in a sentence, and the batch stores the event time zone, anchor instant, projected instant, behavior and note it was approved with.
- **Review before approval.** The review shows the projected send time in the event's zone, the DST note, the template version, the delivery mode, the number who will receive it and who is left out with a count per reason. Its SHA-256 fingerprint covers the audience fingerprint, the template version and wording, the rule, the projected instant, the delivery mode and the reviewed targets; saving and approving both need the fingerprint that was shown (`PREVIEW_CHANGED` otherwise). The page never receives an address.
- **The approved list.** Approval freezes the reviewed recipients as `ScheduledEmailRecipient` rows (an address and the registration it is for). Send time can only remove people from that list, never add anyone: someone who registers afterwards is not messaged by a schedule a person did not review.
- **Re-evaluation.** When a batch is due the whole audience is evaluated again through the builder's own rules, as the approver's *current* permissions allow, and every approved recipient is kept or dropped with a code: registration no longer on the event, cancelled or not submitted or confirmed, contact changed (a transfer), no longer matching the approved audience, no balance due (balance reminder only; an organization-billed event never gets one), no or invalid address, opted out (announcements only), bounced or complained, or a minor. Immediately before each message is captured or sent, `scheduledEmailObsoleteReason` (called once per message, right before the provider call, and outside any open transaction on the local-capture path) re-reads that recipient's registration with the **same filtered search, narrowed to that one registration** (`enumerateOperationsRegistrationIds` takes the ids), so payment state, tags, location, form answers and the approver's filter permissions are applied again, along with status, contact, balance, suppression and age. It also checks the batch is not cancelled or paused, that the approver may still send, that the message is not later than six hours after its time or past its anchor, and, if the audience's filter can no longer be applied (stale, the audience grew too large, or the approver lost the permission to use it), it returns `FILTER_UNAVAILABLE` rather than throwing. An obsolete message ends `CANCELLED` with the reason on the row and on the recipient, and the private link its body minted is withdrawn. A message that names a schedule but is linked to no approved recipient is never sent. If the check itself cannot be made, the message is retried (or left `PENDING` when capturing locally), never sent on a guess.
- **Gates at send time.** The approver lost `MANAGE_COMMUNICATIONS`, the event's time zone or the projected instant changed, the template was published again since approval, or a filter the audience uses is no longer available: the schedule is `PAUSED` for a new review, with the reason shown. If a worker had already queued messages (a takeover after a crash), a gate **fails** the batch instead (a paused batch could be edited or approved again under messages already in the queue), cancelling what is still waiting and keeping what was sent. A schedule more than six hours late is `FAILED` rather than sent late.
- **Idempotency.** One worker claims a due batch with a conditional update (`claimToken`); a second claim fails. Recipients are unique on batch, registration and address; every queued message is an outbox upsert on a key derived from the batch, registration and address; each chunk of messages is queued in a transaction that first re-confirms the worker still holds the claim on an `ACTIVE` batch, which also serializes with pause and cancel (the same conditional update on the batch row). A stale claim (ten minutes) with recipients still to queue can be taken over; a re-run reuses the messages already queued. A scheduled message is never copied by a retry (single or "Retry failed"): its schedule owns retries, so a copy cannot escape the checks or the cancel.
- **In the sweep.** Scheduled dispatch runs after the core queues (`processPendingMessages`, account email), at most three batches per sweep and not started once a 60-second budget is spent; the local-capture step honours the same deadline and leaves the rest `PENDING` for the next queue pass. What a batch queues for real email is delivered by the next sweep.
- **Pause and cancel.** Before a claim, pause or cancel stops everything; nothing was queued. After a claim and partial delivery, cancel keeps every message already sent or being sent and cancels only the rest (the outbox rows that are still `PENDING`, and the recipient rows that were not yet sent), and the audit row says how many sent messages were kept.
- **Youth.** Owner decisions (issue #177, Oct 15 and Oct 17, 2026): a youth's own address is written to **only when an adult is genuinely behind it in that send**. The builder excludes minor attendees by attendee type (minimum age 18 or more is adult; unknown is not). A second, independent rule (`refusedYouthTargets`, loaded by `findMinorTargets`) runs at review, at approval, when each recipient is queued and again before each send, on the roles the recipient holds *now*:
  - An address is a youth's when it is the own address of a minor or age-unknown attendee anywhere in the event, or the contact address of a registration whose account holder is a minor.
  - The account holder is judged across the **whole event**: a Person who is a non-adult attendee on any registration is a minor everywhere, and an account holder who attends nothing is an adult parent and is not blocked.
  - What vouches for a youth address: a group billing or organization contact holding that role now, the registration contact when the account holder is not a minor, or an adult-type attendee of the registration holding the address. A minor account holder never vouches, so a youth who types a younger sibling's address as the contact, or is their own contact through the account-holder fallback, is never emailed. A lapsed leader role cannot vouch.
  - Any other address reached only as an attendee needs an adult-type attendee holding it.
- **Real-database check:** `npm run test:scheduled-emails` (a stand-in email provider, a spring-forward schedule, three concurrent workers, partial delivery and cancel, the youth cases, edits and every send-time gate).

## Central email: effective delivery (#1043)

Real email is on for every event. There is no per-event delivery switch and no per-event sender address.

- `effective-delivery.ts` is the one place that decides whether an event's email is sent. **Paused** (`EventMessageSettings.deliveryPaused`, set only by a system administrator on System management > Email, audited with ids only) is capture only. Otherwise the platform mode applies: real email where account and provider email is configured in this environment and the central sender address is set, capture locally where it is not (development and CI). The `deliveryMode` field on the objects it returns is that effective mode.
- The From address is always the central sender (`PlatformSettings.defaultSenderEmail`). An event overrides only its display name (`senderName`) and reply-to (`replyToEmail`); `senderEmail` and `deliveryMode` on `EventMessageSettings` are retired and read only by migration `20261114100000_central_email` and `central-email-preview.ts`.
- Every send path, retry and readiness check calls `loadEventEmailSettings`, `loadEventEmailSettingsOrThrow` or `getEffectiveDelivery`. `tests/effective-delivery-1043.test.ts` fails if any other file reads `EventMessageSettings.deliveryMode` or `senderEmail`.
- In development, with real provider credentials in the environment and a central sender set, seeded and new events now send real email; pause them on System management > Email, or leave the credentials unset to capture.
- If the environment can send but the central sender is blank, the reason is `SENDER_MISSING`: messages queue and stay PENDING (never captured, so never lost), delivery refuses with EXTERNAL_EMAIL_NOT_CONFIGURED, and the Email page and readiness say "Central sender not set; emails are waiting". They send once the sender is saved.
- Before applying the migration, `npm run email:migration-preview` (read-only) lists the events it will pause and the events whose own sender email differs from the central one.

## SES bounces, complaints and suppressed addresses (#863)

Amazon SES reports deliveries, bounces and complaints through an SNS topic that posts to `POST /api/webhooks/ses` (setup is a human step: `docs/DEPLOY-DOCKER.md`).

- **Transport and meaning are separate.** `integrations/email/ses-sns.ts` verifies the SNS envelope (signature versions 1 and 2, the allowed topic `SES_SNS_TOPIC_ARN`, the allowed account `SES_AWS_ACCOUNT_ID`, a signing certificate and a subscription address only on `sns.<region>.amazonaws.com`) and parses the SES notification. `ses-event-repository.ts` stores it and `provider-events.ts` maps it onto the shared delivery status (`mapSesDeliveryEvent`). Nothing is fetched from an address the payload chose unless it passes those checks.
- **Replay-safe.** One `MessageProviderEvent` per SNS `MessageId` (`provider: "SES"`). A message is matched only by `provider: "SES"` and the exact normalized id the adapter recorded (`normalizeSesMessageId`); an unknown id is held unlinked and attaches to nothing. `providerAdvanceCondition` makes the status write conditional, so a terminal state (bounce, failure, complaint, suppression) is never rolled back by a duplicate or late report.
- **Suppression (Caleb's decision).** A hard (permanent) bounce or a complaint writes an `EmailAddressSuppression` row (normalized address) and stops ALL email to it. A soft bounce is recorded only. `effective-delivery.ts` owns the decision (`checkRecipientDeliverable`); the one delivery worker applies it right before the provider call (and again after the body is prepared), fails closed, and ends the message `SUPPRESSED` with a reason and an audit row (ids and the reason, never the address). Only a system administrator can re-enable an address (`reenableSuppressedAddress`, audited, same-origin only); an event that happened before the re-enable can never switch it back on.
- **What staff see.** "Not sending: bounced" or "Not sending: complaint" on the registration (contact and attendee), and the list with Re-enable under System management > Email > Email health.
- **Privacy.** Stored payloads, logs and audit entries hold ids and counts only. The address lives only on the suppression row.
